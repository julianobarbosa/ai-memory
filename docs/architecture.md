## Executive summary

ai-memory is a **single long-running server** (the `ai-memory` binary in `serve` mode) that
agent CLIs talk to over HTTP (and MCP). The server owns two sources of truth kept in lockstep:
a **markdown wiki on disk** (git-versioned) and a **SQLite index**. Everything else is a layer
around that spine. The CLI is a **thin HTTP client** — subcommands never touch SQLite or wiki
files directly; the server is the single source of truth.

The defining architectural choices, all traceable to documented failure modes of prior tools
(cognee, agentmemory, basic-memory — see `docs/issues-*.md` and `docs/research-*.md`):

- **Single-writer SQLite actor.** Exactly one OS thread owns the write connection; callers send
  commands over an mpsc channel and await a oneshot reply. This structurally eliminates SQLite
  `database is locked` errors under tool-heavy agent fan-out.
- **Write-through wiki.** Every page mutation writes the markdown file *and* updates the SQLite
  index in the same call — no background-after-return indexing, so the index never diverges.
- **Typed privacy boundary.** Nothing becomes a persisted observation without passing through
  `Sanitizer` / `Sanitized::new` — enforced at the type level.
- **Pluggable LLM behind a trait.** Everything takes `Arc<dyn LlmProvider>`; provider choice is
  external, and structured output is schema-constrained per provider.
- **Content-addressed supersession.** Pages are versioned in place: identical body (same
  sha256) is a no-op; a changed body creates a new `is_latest` row linked via `supersedes`.

## Layered structure

```
                         ┌─────────────────────────────────────────────┐
  Agent CLIs ── HTTP ──▶ │  ai-memory serve  (one axum app, one port)  │
  (hooks + MCP)          │                                             │
                         │  /mcp   → ai-memory-mcp  (16 memory_* tools) │
                         │  /hook* → ai-memory-hooks (lifecycle ingress)│
                         │  /admin → ai-memory-mcp::admin (CLI ops)     │
                         │  /web   → ai-memory-web  (read-only browser) │
                         │  /api/v1→ ai-memory-web  (JSON API)          │
                         │  /workstream/* → ai-memory-hooks             │
                         └───────────────┬─────────────────────────────┘
                                         │
        ┌────────────────────────────────┼───────────────────────────────┐
        ▼                                ▼                                 ▼
  ai-memory-consolidate          ai-memory-wiki                    ai-memory-store
  (LLM pipeline + jobs) ──write──▶ (markdown + git,       ──write-through──▶ (SQLite:
        │                          admission chain,                          single-writer
        │  Arc<dyn LlmProvider>    file watcher)                             actor + reader
        ▼                                                                    pool, FTS5,
  ai-memory-llm                                                              embeddings)
  (providers + embedders)
                                   ai-memory-core  ── shared types / IDs / Sanitizer (used by all)
```

`ai-memory-workstream` sits to the side of this spine: it powers `ai-memory run` (managed
cross-harness launches + read-only transcript export), not the wiki/index write path.

## Component overview

### Foundation

- **`ai-memory-core`** — the shared vocabulary, `no I/O`. UUID-v7 newtype IDs; the universal
  identity coordinate is the 3-tuple **`(WorkspaceId, ProjectId, PagePath)`**. Domain records
  come in `New*`/materialized pairs (`NewPage`/`Page`, `NewObservation`/`Observation`,
  `NewHandoff`/`Handoff`, `NewUser`/`User`). Key enums: `Tier`
  (Working→Episodic→Semantic→Procedural), `ObservationKind`, `HandoffState`, `AgentKind` (16
  agent CLIs, with per-agent hook-stdout semantics baked in). Also hosts the privacy
  `Sanitizer` and the CLAUDE.md/AGENTS.md routing-marker helpers.

- **`ai-memory-store`** — the SQLite layer. `Store::open(data_dir)` runs all migrations and
  spawns the writer thread + reader pool. `WriterHandle` (every mutation is a `WriteCmd`) and
  `ReaderPool` (all read DTOs) are the only two handles the rest of the system holds.
  Subsystems: scope resolution, decay/retention scoring, auto-improve staging+approval state
  machine (optimistic concurrency; **pinned pages can never be auto-rewritten**), maintenance
  scheduler, session-consolidation queue, user-token auth, FTS5 query sanitization.

- **`ai-memory-wiki`** — the only correct write path to disk. On-disk layout
  `<wiki_root>/<workspace_id>/<project_id>/<page-path>`. Atomic temp-file+rename writes,
  frontmatter parse/emit, `GitAdapter` for checkpoints/commits, a debounced filesystem watcher,
  and an **admission-webhook chain** (sync HTTP hooks that may mutate frontmatter/body before
  persistence). Every mutation writes the file and sends `WriteCmd::UpsertPage` in one call.

### Consolidation & intelligence

- **`ai-memory-consolidate`** — the "Karpathy LLM Wiki" pipeline. `Consolidator` turns a
  session's raw observations into distilled, versioned wiki pages via `Arc<dyn LlmProvider>`.
  `Bootstrap` seeds a project's wiki from pre-existing history (git log, README, docs/).
  Structured-output types (`ConsolidatedPage`, `PageKind`, `SlotKind`) are schema-constrained
  so providers can't drift (e.g. `tier` is a closed enum, not a free string). Also hosts the
  maintenance jobs: `run_lint`, `run_sweep` (decay eviction), `run_curator_report`,
  `run_embedding_backfill`, and the auto-improve review/scheduler/telemetry.

- **`ai-memory-llm`** — provider-neutral abstraction, but with **native strict `reqwest`
  clients per provider** (deliberately not a generic gateway — the design cites LiteLLM/Instructor
  silent-kwarg-drop bugs). `trait LlmProvider` + `complete_structured::<T>()`; separate
  `trait Embedder`. Providers: Anthropic (key + OAuth), OpenAI, Gemini, OpenAI-compat
  (Ollama/vLLM/LM Studio), OpenAI OAuth (ChatGPT/Codex), GitHub Copilot, OpenCode Zen.
  Embedders: OpenAI, Voyage, Google. Homegrown OIDC device-code flow for OAuth providers.

### Interfaces

- **`ai-memory-mcp`** — the MCP server (`rmcp`, pinned protocol version). 16 `memory_*` tools
  on `AiMemoryServer` (see [`api-contracts.md`](./api-contracts.md)). A separate plain-HTTP
  `/admin/*` router (~30 routes) carries state-touching CLI operations. Four-rung auth
  (Anonymous/User/Root) with constant-time token compare. Handles the stdio-vs-HTTP identity
  difference (stdio = anonymous actor; HTTP = middleware-injected `ActorContext`). A
  `?flavor=moonshot` tool-list rewrite strips schema constructs Kimi/Moonshot clients reject.

- **`ai-memory-hooks`** — the lifecycle-hook HTTP ingress (`/hook`, `/hook/batch`, `/handoff`,
  `/workstream/*`). Every tool call and prompt becomes a bounded, sanitized observation;
  `SessionEnd` triggers session-page synthesis (rule-based, or LLM via consolidate when a
  provider is configured). Bounded everything (in-flight semaphore, per-source rate limit,
  idempotency via `ingest_key`) to protect the single writer under fan-out. Vendored client
  hook scripts spool locally and drain fire-and-forget so the agent never blocks.

- **`ai-memory-web`** — read-only wiki browser mounted at `/web` + a `/api/v1` JSON API for
  third-party frontends. `axum` + `askama` templates + `pulldown-cmark`. Registered *before*
  the bearer-auth layer; CORS scoped to `/api/v1` only. Theme follows `prefers-color-scheme`.

- **`ai-memory-workstream`** — read-only native-harness adapters for `ai-memory run`. Plans
  managed launches (`build_launch_plan`, `--yolo` translation, new/adopt/resume logic),
  fingerprints repository/worktree identity, and incrementally exports native session
  transcripts into portable events with a resumable cursor. **Never mutates** the checkout or
  the native session store.

### Composition

- **`ai-memory-cli`** — the `ai-memory` binary and top of the dependency graph. Loads config
  once (`figment`), dispatches ~50 clap subcommands. `serve` builds `AiMemoryServer` +
  `admin_router` + `hook_router` + `workstream_router` + web under one axum app with shared
  bearer auth (or runs the MCP server over stdio). `hook`/`hook-drain`/`completions`
  short-circuit before config/tracing load to stay cheap and emit only JSON. Destructive
  commands default to dry-run and require `--confirm`/`--apply`.

## Cross-cutting invariants

These are load-bearing and enforced (many with dedicated tests):

1. **One SQLite writer.** All mutations serialize through the single writer actor.
2. **Config read once** at startup; no scattered env reads in library crates — config is
   threaded in as typed state.
3. **Atomic file writes** (temp + rename) for every wiki page.
4. **CLI is always a thin HTTP client** — never touches SQLite/wiki directly.
5. **Sanitize before persist** — the type system makes it impossible to skip.
6. **Pinned pages are never auto-rewritten** by auto-improve (enforced at the shared apply point).
7. **`unsafe_code = "forbid"`** workspace-wide.

## Testing strategy

Standard Rust `cargo test`, no external runner. Per-crate integration tests in
`crates/<crate>/tests/` plus in-module `#[cfg(test)]` units (some files are ~60% tests — e.g.
`ai-memory-web/src/mount.rs`). Root `tests/` holds shell tests (`tests/hooks/test_lib.sh`,
`tests/e2e/handoff_smoke.sh`). CI additionally builds the release binary and runs a Docker
smoke test. See [`development-guide.md`](./development-guide.md).

## Deployment architecture

Single binary, single port (default **49374**). Runs local (loopback) or on a homelab box
(LAN/VPN/cloud) with bearer-token auth. Distribution: Docker Hub (multi-arch amd64+arm64),
AUR (`ai-memory` / `ai-memory-bin`), native macOS/Windows tarballs, `cargo install`. Native
Linux ships systemd units (system + user). TLS via Caddy or Cloudflare Tunnel compose files.
See [`deployment-guide.md`](./deployment-guide.md) and [`deploy.md`](./deploy.md).
